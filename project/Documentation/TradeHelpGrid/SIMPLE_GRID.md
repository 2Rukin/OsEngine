# THG-SIMPLE-017: Futures2GridSimple

**Статус:** CURRENT IMPLEMENTATION CONTRACT / OPERATOR GUIDE — OFFLINE ONLY.
**Дата:** 2026-09-30. **Основание:** поручение выделить упрощённый вариант
Futures2Grid с ручными границами, шагом, наценкой и лотами на зону.

Это отдельный обычный `BotPanel`, имя в списке роботов — **Futures2GridSimple**.
Робот использует `Futures2Controller`, `Futures2NativeAdapter`, native Journal
и signed-price gateway полного [Futures2Grid](ADR-0002_OSENGINE_IMPLEMENTATION.md).
Полный робот и его параметры сохраняются. Simple имеет собственные параметры
и checkpoint-каталог, поэтому не подхватывает существующую кампанию полного робота.

## Основные настройки

Подключить инструмент на **первой** вкладке Simple. Вторую оставить ненастроенной:
это резерв общего двухendpoint-адаптера, Simple не выполняет перенос контрактов.

В Тестере: выбрать первую вкладку → «Настройки данных» → выбрать инструмент
в окне «Подключение потока данных» → «Принять». Выбор имени не означает, что
асинхронная подписка уже получила Security. При отключённых событиях подписка
Тестера может ещё не привязать сервер; проверить события и загрузку исторических
данных. Запуск replay сам по себе не является обязательным условием получения
описания инструмента.

Если инструмент не выбран или его описание ещё недоступно, Apply/Start показывают
разные сообщения подготовки в System log без exception stack trace. Повтор одного
состояния не засоряет журнал; план не создаётся и команда не включает торговлю.
После готовности нужно повторить Apply/Start. Только уже включённый Regime=On
в симуляции продолжает автоматическую подготовку на следующем проходе с котировкой
и готовым инструментом. Live по появлению метаданных сам не запускается.
При изменении параметров существующей кампании без доступного инструмента
Simple запрашивает паузу входов и сохраняет принятый план.

| Поле Parameters | Значение |
|---|---|
| `Regime` | `Off` запрещает новые входы и отменяет работающие входы; выходы остаются под сопровождением. `On` разрешает работу после подготовки |
| `Direction` | `Long` — покупки с продажей дороже; `Short` — продажи с выкупом дешевле |
| `Lower bound`, `Upper bound` | Включённые нижняя и верхняя цены сетки |
| `Grid step` | Точное расстояние между соседними уровнями в единицах цены |
| `Markup per zone` | Общая положительная наценка от фактической средней цены входа, в единицах цены, не проценты |
| `Lots per zone` | Положительное максимальное количество native контрактов на каждый уровень новой версии плана |
| `Zone markup overrides` | Необязательные отдельные наценки: `1=2;3=4` |
| `Zone lot overrides` | Необязательные отдельные количества: `1=3;5=2` |

**Зона 1 всегда соответствует нижней цене**, в обоих направлениях. Под зоной
Simple понимает один ценовой уровень, включая обе границы. Номер не является
внутренним нулевым LevelId: Long внутри движка перебирает уровни сверху вниз.
Пустое поле overrides означает общие значения. Разделитель пар — точка с запятой;
десятичный разделитель в значении — точка или запятая. Повтор номера, неизвестная
зона, нулевое/отрицательное значение, лишний разделитель или malformed запись
отклоняют весь новый план.

Формула: `N = (Upper - Lower) / Step + 1`, от 2 до 10000 уровней.
Ширина должна делиться на шаг без остатка. Границы, шаг и наценки должны быть
кратны тику инструмента и представимы до пяти знаков. Нулевые и отрицательные
цены допустимы. Объёмы проверяются на native precision/step/minimum; инструмент
с минимумом в денежном notional вместо контрактов отклоняется.

Пример: Lower=100, Upper=110, Step=2, Markup=1, Lots=1 даёт цены
100, 102, 104, 106, 108, 110. `Zone lot overrides=1=3;6=2` задаёт объёмы
3, 1, 1, 1, 1, 2. `Zone markup overrides=1=0,5;6=2` меняет наценки только
у нижней и верхней зон. Шаг3 при таких границах отклоняется, а не растягивается.

## Исполнение и денежные ограничения

Simple сохраняет обычный immediate режим Futures2: Long входит, когда Ask
достиг уровня или ниже; Short — когда Bid достиг уровня или выше. При старте
внутри диапазона уже достигнутые уровни могут последовательно набраться по
текущей лучшей цене. Это не постановка всех resting-заявок заранее.
Обычные заявки лимитные, один новый action за проход, стандартный интервал250мс.
Исходный расчёт Long target = фактическая средняя входа + наценка зоны;
Short target = средняя входа − наценка. Затем результат округляется к тику:
вверх для Long, вниз для Short. Средняя частичных исполнений может быть вне тика.
Выход отправляется по достижении target соответствующей стороной
котировки. После выхода зона снова доступна для входа. Общий движок учитывает
partial fills, занятый объём и ещё исполнимый остаток заявки; неизвестный результат
не освобождает резерв. Рабочая заявка старше30с отменяется общим движком и после
подтверждения может быть выставлена снова, если условия сохраняются.

Границы задают геометрию, **автоматического стопа на границе нет**. Long ниже
нижней границы может добрать ещё не заполненные уровни; Short выше верхней —
аналогично. `Emergency flatten` отдельно защёлкивает ликвидацию принадлежащего
роботу объёма через общий cancel-confirm процесс. Это локальное управление,
не заранее поставленная брокерская защитная заявка.

Во вкладке Safety вручную задаются `Collateral per lot` (положительное ГО за
native контракт) и `Funds limit` (выделенный денежный предел). Расчётная единица
учёта Simple — RUB. План требует `sum(zone lots) × collateral <= Funds limit`.
Известное брокерское ГО выше ручного запрещает построение/новый вход. Capital
общего движка равен именно резерву всей сетки, а не всему Funds limit. Этот же
Capital передаётся адаптеру как manual funds envelope; старые позиции и ещё
исполнимые входы продолжают расходовать общий резерв при смене плана.
Объёмы не увеличиваются автоматически от большого значения Funds limit.
Денежный результат использует PriceStepCost инструмента; при отсутствии — линейную
модель tick × max(1, Lot). Поле результата не доказывает точность реального ГО,
комиссий или валютного пересчёта. Процентные helpers Simple отключены.

Для live нужна явная `Signed order capability selected` и поддержка текущего
профиля коннектором. Это операторский opt-in, а не подтверждение квалификации
площадки. В Tester/Optimizer native signed путь выбирается автоматически.
Интерпретация ValueCurrent−ValueBlocked как available funds не используется.
TRANSAQ сохраняет ограничения [текущей интеграции](FINAM_TRANSAQ_IMPLEMENTATION.md).

## Применение во время работы и восстановление

`Preview and status` показывает принятый план и отдельно preview текущих полей,
статус/причину, pending ID, capital, native/account gate, последние50 intents,
идентификаторы заявок и принадлежащие лоты. В каждой таблице выводятся первые200
зон с явным сообщением об ограничении. Ошибки параметров и команды попадают в
штатный Error log; переходы общего адаптера и ожидаемое отсутствие метаданных
инструмента — в System log. Preview без инструмента показывает ожидание его
параметров, а не ошибку построения.

`Apply configuration` проверяет новый snapshot. Если он идентичен принятому или
pending плану, новая версия не создаётся. Изменённые параметры из штатного окна
применяются через тот же путь. Невалидное изменение из окна параметров переводит
Regime в Off и запрашивает pause входов; ранее принятый план сохраняется. Ошибка
кнопки Apply показывается в диагностике, сама кнопка не выключает старый план.

Смена только per-zone наценки/лотов также создаёт новую версию: добавлен явный
пятиаргументный `Configure(..., replaceLevelSettings: true)`. Четырёхаргументный
API полного Futures2Grid сохраняет прежнее правило reuse равного Input и ручных
level edits. Смена Simple ждёт подтверждений отмены конфликтующих заявок.
Старые лоты, включая cancellation-time fills, сохраняют PlanId и прежнюю
наценку до закрытия; новые настройки относятся к новым входам. Старые и новые
планы совместно ограничены Capital. Если новый резерв меньше уже удержанного,
публикация отклоняется: нужно закрыть/уменьшить объём либо вернуть достаточные
параметры. Направление нельзя менять с открытым объёмом.

Если публикация завершилась при Off и остались лоты, на следующем проходе
котировки/live timer Simple восстанавливает PausedEntries из общего Ready.
Входы остаются запрещёнными, обычные выходы снова рассматриваются при тех же
reconciliation/freshness gates; дополнительная ручная команда Pause не нужна.

```mermaid
sequenceDiagram
    participant U as Оператор
    participant S as Simple
    participant E as Общий движок
    participant N as Native Journal и коннектор
    U->>S: Изменить границы, шаг или настройки зон
    S->>S: Проверить тик, объёмы, ГО и лимит
    Note over S: Если метаданные инструмента отсутствуют, показать ожидание и закончить команду до Configure
    S->>E: Configure полного нового плана
    E->>N: Запросить отмену конфликтующих заявок
    N-->>E: Исполнения и окончательные статусы
    E->>E: Сохранить старые лоты; опубликовать новый план
    E-->>S: Active или Ready; причина и PlanId
```

Live checkpoint: `Engine/Futures2GridSimple/<hash(robot name)>.json` плюс native
Journal. После рестарта требуется сверка: проверить заявки/счёт, указать
`Owner verified account and orders`, выполнить `Reconcile native and account`,
затем `Start or resume`. Одного сохранённого Regime=On недостаточно. Неизвестную
заявку нельзя повторять вслепую; `Resolve verified absent order` требует
проверенных брокерских фактов, intent ID и исполненного количества. После
emergency доступна только явная `Rearm after confirmed flat`, затем Start.

`External net` объявляет независимый от робота net по инструменту; он не
регистрирует ручную сделку как принадлежащую Simple. Необъявленное расхождение
блокирует сверку. Команды атрибуции ручных покупок/продаж, HJ, trailing, перенос
контрактов, portfolio transfers и автоматические range-команды остаются в полном
Futures2Grid. Они не включены скрыто в Simple.

В Tester/Optimizer поставить Regime=On перед прогоном. TestingStart очищает
симуляционное состояние; первая котировка готовит план, выполняет локальную
сверку и стартует. Диск кампании не используется. Все команды/callbacks работают
под Sync адаптера, live timer250мс принадлежит роботу; удаление снимает подписки,
останавливает timer и закрывает окно диагностики через dispatcher.

## Проверки и граница evidence

Default managed suite `Tests/TradeHelpGrid/SimpleCases.cs` проверяет exact-step
signed/zero geometry, направление и zone mapping, дробные native количества,
10000-уровневую границу, отказ невалидных параметров, override-only drain,
late partial fill старого плана, сохранение старого Configure API, retained
collateral, submit-pending restart и discovery имени в BotFactory. Отдельная
регрессия вызывает настоящий BeforeDecision на managed host fixture после
отмены выхода и публикации при Off: проверяет возврат выхода старого лота без
нового входа для live/simulation ветвей и паузы до/после Configure. Никакой
реальной live сессии эта ветка fixture не создаёт. Набор не
конструирует робота, не запускает GUI/Tester server и не отправляет native заявки.

Команды из `project/`:

```text
dotnet build OsEngine/OsEngine.csproj --no-restore
dotnet build OsEngine.sln --no-restore
dotnet run --project Tests/TradeHelpGrid/OsEngine.TradeHelpGrid.Tests.csproj --no-build
```

Результаты текущего checkpoint фиксируются в ACTIVE_TASK. Историческое SRU6
evidence полного Futures2Grid не считается отдельным прогоном нового Simple host.
Физические UI/Tester/Optimizer/live проверки пока OWNER-RUN: создание из списка,
настройка первой вкладки, два последовательных replay с Regime=On, preview и
изменение overrides при открытой позиции; для live — отдельный разрешённый
сценарий восстановления и сверки. Успешная сборка/managed suite не доказывает
profitability или Tester/live parity.
