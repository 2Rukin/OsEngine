# ADR-0001 — Статистика исторических данных и разности фьючерсов

Дата: 2026-09-18. Статус: Accepted for implementation.
Результаты архитектурного ревью: [0001-review.md](0001-review.md).
База: `2Rukin/OsEngine`, `master`, `f54de33961d45f73319ae1c7313f2854bcb27398`.

## Задача

Из главного меню открыть самостоятельное окно, выбрать папку датасета OsData,
две серии фьючерсов и исследовать разность A − B в совместно активной части
истории. Первый сценарий — обыкновенный Сбербанк (A, SR) минус привилегированный
(B, SP), предпочтительно одной экспирации. Тикеры не зашиваются в расчёты.
Дальнейшие анализы одиночных фьючерсов должны переиспользовать чтение истории.

## Точки подключения и границы

- `MainWindow.xaml`: кнопка Statistics в свободной строке блока Trading над Robots.
- `MainWindow.xaml.cs`: локализованная подпись, парольная блокировка, открытие
  единственного принадлежащего главному меню окна; повторный клик активирует его.
- `OsData/Statistics/`: XAML/code-behind, read-only адаптер датасета, независимое
  от WPF ядро расчётов и модели результата. Никаких торговых серверов/ордеров.
- Стиль штатного окна, динамические ресурсы темы, RU/EN через OsLocalization.
- Конструктор `OsDataSet` запускает WorkerArea; `SecurityToLoad.Load` вызывает
  ActivateLoaders с созданием каталогов. Поэтому для офлайн-каталога они
  **не используются**. Небольшой read-only адаптер читает идентификационные
  поля формата Settings; поддерживает текущий и старый варианты строк.
- Реальные доступные файлы сверяются с каталогом Settings. Стандартный путь
  `<dataset>/<sanitized security>/<TimeFrame>/<sanitized security>.txt`.
  Внутренние Temp, тики и стаканы не выдаются за свечи. Метаданные Settings —
  не доказательство наличия истории, ликвидности или фактического диапазона дат.
  Корень поиска — выбранная пользователем папка, а не сохранённый SetName.
  Имена из Settings не могут задавать абсолютные пути или выходить за этот
  корень; неоднозначные совпадения файлов/имён не разрешаются молча.

## Математический контракт

1. Обе ноги выбираются явно из каталога; одинаковый файл недопустим.
   Таймфрейм должен совпадать. Пользователь отвечает за совместимость единиц
   котирования и экспираций. Автоматической склейки разных серий нет.
2. В первой версии только `basis(t) = CloseA(t) − CloseB(t)` в единицах исходной
   цены, коэффициенты 1 и 1. Это не денежный PnL и не гарантия арбитража.
3. Вход — свечные строки `DATE,TIME,OPEN,HIGH,LOW,CLOSE,VOLUME[,OPEN INTEREST]`.
   Числа invariant, даты `yyyyMMdd,HHmmss`; OI необязателен и не участвует
   в фильтре. Нулевой OI не трактуется как отсутствие ликвидности.
4. Строго возрастающие временные метки, без дубликатов. Некорректные строки,
   отрицательные объёмы и невалидные OHLC останавливают расчёт с файлом/строкой.
   Отрицательные цены допустимы; валидность OHLC означает согласованность
   High/Low/Open/Close, а не положительность цены.
   Нет молчаливого исправления, сортировки, forward-fill или интерполяции.
5. Фильтр дат включителен по календарной дате исходных меток; преобразования
   часового пояса нет. Предполагается одинаковая временная зона обеих ног.
6. Для каждого дня в объединении дат обеих ног считаются объём и число свечей
   с положительным объёмом отдельно для A и B. Синхронная активная точка —
   одинаковое время свечей и положительный объём обеих ног.
7. День проходит фильтр при достижении заданных минимумов суточного объёма
   каждой ноги, числа активных свечей каждой ноги и покрытия
   `100 × matchedActive / unionActive`. Нужна минимум одна синхронная точка.
   Сравнения включительны (`>=`); объёмы и числа активных свечей считаются
   по собственным данным каждой ноги за весь выбранный день, до синхронизации.
   UnionActive — число различных временных меток с положительным объёмом
   хотя бы одной ноги; нулевой знаменатель означает отклонение дня.
   Минимальные объёмы неотрицательны, минимальные числа свечей положительны,
   порог покрытия находится в диапазоне от 0 до 100 процентов включительно.
   Пороги задаются пользователем; начальные 1 / 1 / 1 / 1 / 80% — лишь
   демонстрационные настройки, не универсальная оценка ликвидности.
8. В итог входят только синхронные активные точки прошедших дней. Покрытие
   измеряет совпадение имеющихся свечей, не полноту торговой сессии. Полностью
   отсутствующий в обоих файлах день нельзя отличить от выходного без календаря.
   Дневной фильтр ретроспективный, не предназначен для сигналов без look-ahead.
9. Для прозрачности отображаются все наблюдаемые дни, объёмы, активные свечи,
   совпадения, покрытие, решение фильтра и дневные min/max/range для принятых.
   Участки разделяются отклонённым наблюдаемым днём ИЛИ пропуском календарной
   даты (консервативно также выходными), чтобы не обозначать пробел как историю.
10. Итоговые min, max, размах max−min, среднее, population stddev, число точек,
    начало/конец, принятые/отклонённые дни. Нулевой результат — понятное сообщение,
    не нулевые min/max. График/таблица точек и дневная диагностика позволяют
    проверить результат. В первой версии ряд отображается виртуальной таблицей
    полностью, без прореживания; график и экспорт отложены.
    Среднее невзвешенное по принятым точкам; population stddev использует
    делитель N. Для одной точки размах и stddev равны нулю. Общий результат
    считается по всем принятым точкам, не усреднением дневных статистик.

Фильтр объёма/активности — настраиваемый proxy ликвидности, а не оценка
доступного стакана, bid/ask или гарантированного исполнения. Отображаемые
экстремумы и размах относятся к синхронным Close-спредам.

`HighA − LowB` и `LowA − HighB` не являются наблюдаемыми экстремумами спреда:
экстремумы двух инструментов могут происходить в разное время. Даже Close
одного интервала не гарантирует одновременность последних сделок внутри него.

## Производительность и жизненный цикл

Чтение и расчёт выполняются в фоновой задаче без async void. UI получает только
готовый результат через Dispatcher; параметры фиксируются перед запуском.
Одна операция на окно, отмена через CancellationToken при Cancel/Close.
Исходные файлы открываются без разрешения конкурентной записи на время чтения;
растущий/перезаписываемый датасет следует остановить перед анализом.
Ресурсы чтения закрываются и при ошибке/отмене, результат не публикуется после
закрытия. Отмена не выдаётся за ошибку. Большие ряды имеют явный защитный лимит
с предложением сузить диапазон; никаких молчаливых усечений расчёта.

## Расширение

Чтение свечей, фильтрация и результат не зависят от MainWindow или торговых
табов. Новые анализы добавляются как сервисы над тем же входом. Плагинный
фреймворк, бэктест, комиссии, торговля, автосклейка/автоподбор серий,
коинтеграция и денежная нормализация не входят в первый этап.

## Отклонённые варианты

- BotTabPair/BotTabIndex: связаны с коннекторами/торговым жизненным циклом;
  не нужны для детерминированного анализа файлов без подключения к рынку.
- Ликвидный период между первой и последней ненулевой свечой: маскирует
  внутренние неликвидные дни и пробелы.
- Ближайшие по времени свечи и заполнение пропусков: создают искусственный спред.
- Фиксированные «правильные» пороги для Сбера: не переносятся на другие фьючерсы.

## Проверка

Автотесты чистого ядра: знак A−B, отрицательная разность, константа/одна точка,
точное выравнивание, нулевой объём, пороги и границы покрытия, отсутствие общей
истории, разрывы участков, даты, дубликаты, ошибки парсинга, текущий/старый
Settings, отсутствие побочных записей, отмена и лимиты. Ручная Windows-проверка:
кнопка/пароль, повторное открытие, RU/EN, темы, выбор датасета, фон/отмена/закрытие,
сравнение дневной таблицы с исходными строками. Сборка основного проекта;
MCP-стенд не запускать.
