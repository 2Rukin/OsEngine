# 07. Tester, golden-сценарии и ручная приёмка

Цель: сначала доказать поведение, затем исследовать экономику. Все результаты ниже — **ожидаемые эталоны**, не выполненные прогоны OsEngine. Состояние реальных проверок публикуется отдельно.

## Golden-профиль для чистого ядра

A=100; Long; S=90; U=110; InitialVolume=10; MaxVolume=20; MinActiveVolume=1; lot=1; Wadd=5; Wreduce=10; FixedScales; γinv=0; MinRebalanceVolume=1; VolumeDeadband=0; RearmDistance=1; MinActionInterval=0. NoAddZone=[90,93], ρ=0.3. c=1; R=1000; комиссии и slippage=0. FAST выключен. Начальная заявка и каждое действие полностью исполняются по указанной цене fixture до следующего события. Времена событий возрастают на минуту; cutoff заведомо позже всех событий.

Эти упрощения существуют только для проверки арифметики. В NativeTester надо учитывать его реальные fills и задержки. Сценарии S05 и далее явно меняют соответствующие параметры/события.

## S01. Частичный выход и повторная загрузка выше входа

| Цена | Ожидаемое действие | Подтверждённый объём |
|---:|---|---:|
| 100 | Начальный BUY 10 | 10 |
| 102 | REDUCE 2 | 8 |
| 104 | REDUCE 2 | 6 |
| 102 | ADD 2 | 8 |
| 100 | ADD 2 | 10 |
| 104 | REDUCE 4 | 6 |
| 102 | ADD 2 | 8 |

На первой повторной цене 100 позиция восстановлена, CampaignId прежний. Никакой запрет «уровень уже торговался» не возникает. Для первых пяти строк equity при цене 100 равна +8 в синтетических денежных единицах: это проверка ledger, не прогноз доходности. Средняя открытого остатка уже может отличаться от Anchor.

## S02. Повторные циклы ниже входа

| Цена | Ожидаемое действие | Подтверждённый объём |
|---:|---|---:|
| 100 | BUY 10 | 10 |
| 98 | ADD 4 | 14 |
| 96 | ADD 4 | 18 |
| 98 | REDUCE 4 | 14 |
| 96 | ADD 4 | 18 |
| 98 | REDUCE 4 | 14 |

Оба сокращения обязаны состояться даже при цене ниже AverageEntry. Нельзя остановить цикл правилом «тейк только в плюс». Каждое повторение имеет собственные DecisionId/IntentId, но один CampaignId.

| S06 | Цена ровно 90 и затем 88 | ExitLatch, отмена набора и закрытие реального остатка; fill не обязан быть по 90 |
| S07 | После частичных действий цена ровно 110 | Окончательное закрытие; откат к 100 не создаёт повторный вход |

| S13 | При неизменной цене выросла ν или изменился режим | Цель/допуски меняются по формуле; не возникает самовозбуждённого бесконечного цикла fills |
| S14 | Initial 10@100, S=90, R=110, c=1; ADD по 99 | Разрешён максимум 1 контракт при нулевых комиссиях/резерве; 2 дали бы риск 118>110 |
| S15 | Уже есть неисполненный увеличивающий ордер | Его полный возможный остаток учтён в Qmax и риске; повторного ADD на тот же дефицит нет |
| S16 | Частичное исполнение 2 из 5, затем 1, затем отмена 2 | Filled вырос на 3, не на 5; остаток/резерв корректны; fill-дубликат ничего не удваивает |
| S17 | Cancel ADD отправлен, затем STOP, затем поздний fill | Не ждать бесконечно cancel; закрыть известный объём, затем поздний; нет повторного входа |
| S18 | REDUCE и защитный выход конкурируют | Нет избыточного закрытия и переворота при любом допустимом порядке ack/fill |
| S19 | Отказ, timeout отправки, потеря ack | Не считать отсутствие fill доказанным; нет слепого повтора, статус Reconciling |
| S20 | Crash до send / после send до ack / после fill до checkpoint | После сверки те же реальные позиции; новые дубли не созданы |
| S21 | Полный выход, затем старый сигнал и поздний fill | Старый сигнал не открывает кампанию; поздний fill только защитно обрабатывается |
| S22 | Одни данные, seed и параметры; 10 повторов и разные скорости replay | Совпадают canonical decision traces; UI/логи не меняют торговлю |
| S23 | Нет Side для delta-профиля / нет книги для OFI / stale quotes | Явный Missing/NotReady, блокировка набора; никакого фиктивного OFI=0 |
| S24 | Разрыв/повтор sequence, неизвестная точность времени, свежая книга после reconnect | Контроль качества, reset/warmup; нет скачка OFI от пустой книги |
| S25 | Невалидная конфигурация, округления, цена/стоимость шага, чужая позиция | Preflight отказ или безопасная сверка; никакого незапланированного ордера |
| S26 | Нет новых тиков, но наступило SessionExitTime | Таймер запускает защитное завершение; модель не ждёт следующей свечи/сделки |

Для S17–S21 имитация сервера должна переставлять допустимые события детерминированно. Проверка только гладкой ценовой последовательности недостаточна.

## Исторический прогон

Пользователь выбирает tick dataset, интервал и заранее сохранённые входные сценарии. Preflight показывает доступные признаки, warmup, метаданные стоимости шага, комиссии, резерв slippage и модель исполнения. Обычные исторические настройки, имена инструментов и source mode читаются из фактического интерфейса форка; не угадывать их по названию файла.

Запуск: штатный Tester → выбранный APM-робот → data source/параметры → старт. Во время прогона: пауза, переход к следующему событию или решению, просмотр графика и окна «Решения». Специальный переход к следующему решению — функция нового диагностического слоя; не считать его уже встроенным в Tester.

Пользователь проверяет S01/S02 на подготовленных fixture/schedule, затем изучает исторические кампании. В таблице видны решение и отдельные fill events. Нажатие строки переводит график к событию без расчёта с будущими данными.

## Реализм и сравнение

OHLC не доказывает порядок прохождения уровней. TradeOnly не доказывает исполнение Limit по одному касанию. NativeTester может не моделировать частичные исполнения, собственную очередь, market impact и задержки; capability report T01 определяет точные ограничения. Недостающие механизмы испытываются fake broker и отдельно маркируются в отчёте.

Обязательны три cost-сценария: выбранный базовый и усиленные затраты ×1.5/×2 для комиссии и заданного проскальзывания. Это stress assumptions, не измеренные вероятности. Нельзя заявлять реалистичный экономический результат по fixture с нулевыми издержками.

## Пользовательская приёмка M1

Приложить run manifest, таблицу ожидаемого/фактического q для S01–S07, trace, screenshots графика и окна решений, ledger reconciliation, перечень ограничений NativeTester. Пользователь должен увидеть повторную загрузку после частичной разгрузки, пропуски в обе стороны и окончательную остановку. Все эти свидетельства пока имеют статус NOT_RUN.
