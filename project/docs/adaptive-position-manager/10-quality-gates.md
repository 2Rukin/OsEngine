# 10. Quality gates

Gate — проверяемое условие продвижения с артефактами. Статусы: NOT_RUN, PASS, FAIL, BLOCKED, N/A_WITH_REASON. N/A без объяснения запрещён. Документация сама по себе не даёт PASS реализации.

## Неизменяемые блокеры

Блокируют merge реализации в релизную ветку: собственный ADD после ExitLatch; возможное двойное закрытие без обработки; неучтённый cancel-pending риск; отключение защиты частичного начального fill; ложный Completed; неограниченный повтор после timeout; silent lookahead; fake OFI из тиков; общий mutable state optimizer passes; исчезнувшие результаты неудачных trials.

Внешнее вмешательство/изменение брокерского состояния может нарушить фактический q-cap. Система обязана обнаружить расхождение и защитно обработать его. Нельзя формулировать gate как гарантию отсутствия всех рыночных/брокерских сбоев; проверяется недопущение лишнего риска собственными подтверждёнными решениями и корректная обработка наблюдённых отклонений.

## Точность и воспроизводимость

Объём на lot-grid, идентификаторы, состояние и направления совпадают точно. Decimal ledger сверяется по установленному money rounding инструмента; накопленная разница после сверки не более одной минимальной денежной единицы округления, иначе FAIL. Double-признаки: заранее заданные abs/relative tolerance, проверка finite и граничных решений; tolerance не должна скрывать иной ADD/REDUCE.

На одном runtime и manifest десять запусков дают одинаковый canonical trace (исключены run ID, wall-clock logging timestamps и порядок независимого UI). Diagnostics on/off, изменение скорости replay и число optimizer threads не меняют решения. Смена runtime/источника/метаданных требует новой записи окружения.

Для ядра целевой branch coverage ≥90%; критические ветви ExitLatch/risk/reservation проверяются все именованными тестами независимо от coverage percentage. Отсутствие инструмента coverage — BLOCKED для подтверждения этой цифры, не выдуманный PASS.

## Gate эксплуатационной нагрузки

T11 фиксирует ПК, runtime, dataset и замеренный максимум входных событий за секунду. На replay со скоростью не менее 2× этого зарегистрированного потока: ноль потерянных price/fill/order events; нет неограниченного роста очереди; память после прогрева ограничена заданными размерами buffers; остановка не ждёт отрисовки таблиц. Отдельно замеряются p50/p95/p99 ядра, очередь и end-to-end задержка. При недостаточной мощности результат BLOCKED/FAIL, не молчаливое прореживание торговых событий.

Защита SessionExit запускается первым доступным timer event не позже одного настроенного TimerResolution после cutoff в работающем event loop. Задержки брокера/сети отражаются отдельно; их нельзя объявить нулевыми по успешному unit-test.

## Три независимых решения о готовности

1. **Engineering PASS**: реализация соответствует контракту и не имеет блокирующих дефектов.
2. **Research GO / ResearchOnly / NO-GO**: экономический результат оценён на незатронутом периоде, после издержек и stress; выбранный риск-профиль заполнен заранее.
3. **Live authorization**: отдельное явное разрешение пользователя после shadow/paper и проверки реального коннектора.

Для M1 нужны QG00–QG07. Для M2 дополнительно QG08. Для OFI-профиля QG09 обязателен. QG10 необходим только при включении расширенного исполнения, иначе N/A_WITH_REASON. Для live обязательны QG11/QG12 и отдельная авторизация; research GO не отменяет safety gates.

## Review flow

Исполнитель заполняет [форму](templates/task-report.md). Reviewer архитектуры/математики и reviewer безопасности работают read-only; при отсутствии отдельного reviewer честно указать self-review и не выдавать его за независимое. Каждая находка содержит severity, путь/строки, достижимую последовательность событий, эффект и тест воспроизведения. Теоретическая находка отдельно помечается как потенциальная, не скрывается.

Два конечных цикла review: первичная проверка → исправления → повторная проверка. Нерешённый High/Critical после второго цикла — BLOCKED и явное решение владельца, а не бесконечный polishing или снижение severity для прохода. Для гонок приложить текстовую последовательность участников/событий, пригодную для переноса в sequencediagram.org, без вымышленных результатов.

## Git и доказательства

Задание считается DONE только с commit SHA, фактическим diff, командами проверки/exit codes и ссылками на отчёты. Невыполненные проверки остаются NOT_RUN. Нельзя заменить сборку формулировкой «должно собраться». Для текущего документационного коммита code gates NOT_RUN; структурные проверки документации не считаются unit-тестами стратегии.
