## Что ещё не доказано

T01 обязан проверить фактические overloads добавления к существующей позиции, сохранение Side/Id/времени тиков в обеих средах, последовательность callbacks, поведение partial fills, семантику Market и stop-market выбранного коннектора, сброс состояния каждого optimizer pass, совместимость тиков и стакана в одном прогоне, цену/момент исполнения заявки, созданной в обработчике тика.

Нельзя переносить из справочников формулировки «гарантированное исполнение» или «айсберг без проскальзывания» как продуктовые гарантии. Нельзя копировать пример, который выходит из обработчика при IsOsOptimizer: этот робот обязан там считать ту же логику.

Пример `position.State == Open` полезен для штатных методов, но недостаточен для защиты уже исполненного начального остатка. Поведение Opening/Closing/ClosingFail и доступность методов проверяется контрактными тестами адаптера.

## Предлагаемые точки расширения

Рабочие имена: AdaptivePositionManager (чистое ядро), ApmOsEngineAdapter (торговой адаптер), AdaptivePositionResearchBot (оболочка). Размещение ядра — рядом с существующим доменом OsTrader; робота — в пользовательской области `Robots/MyBots/AdaptivePositionResearchBot/`; тестов — под `project/Tests/AdaptivePositionManager/`. Это **предложение путей**, не утверждение о существующих файлах. До создания робота согласовать каталог согласно CONTEXT_ROBOTS_ARCHITECTURE.

Не дублировать брокерскую транспортную систему, Journal и RiskManager. Сохранённый campaign state дополняет движок. Штатный общий риск-менеджер не отключается: APM вводит дополнительные более узкие ограничения. Управление одной позицией со стороны ручного auto-support и APM должно быть согласовано, иначе запуск блокируется.

## Контракт адаптера

Адаптер переводит Market/Order/Fill события в [04](04-data-contracts.md), сериализует их для ядра, переводит Decision в штатные команды и возвращает фактический результат. Методы Open/Add/Reduce/Cancel/Query/Protect обязаны иметь явный capability report. Если безопасное увеличение одной Position недоступно, допускается campaign aggregation нескольких штатных Position только с отдельным ADR, общей защитой, ownership и сверкой без изменения пользовательской семантики.

Время — из тестируемого event clock. В режиме live есть отдельный watchdog. События UI не блокируют торговую обработку. Удаление робота отписывает callbacks; нельзя удалением интерфейса оставлять активную позицию без владельца.

## Совместимость с Tester

Зарегистрировать робота штатным способом и объявить параметры. Входы — из сохранённого CampaignSchedule либо ручной исследовательской команды с последующим экспортом в schedule. Для массового сравнения ручные входы сначала фиксируются; нельзя заново выбирать удобные места для каждого набора параметров.

Первые два режима исполнения — DeterministicFixture (только тест ядра, не реальная ликвидность) и NativeTester (реальные правила выбранного тестера). Они явно различаются в отчёте. OHLC-прогон допускается только как грубый smoke: по одной свече нельзя однозначно восстановить порядок нескольких ADD/REDUCE/STOP.

Нативный Tester не объявляется симулятором собственной очереди/market impact до проверки исходников и capability-test. OFI требует отдельного доказанного потока, а не просто наличия текстового tick-файла.

## Совместимость с Optimizer

Все управляемые параметры через стандартные StrategyParameter, без собственного отдельного оптимизатора. Fixed параметры обязаны действительно сохранять выбранные значения в каждом pass. В каждом прогоне отдельные mutable state, timers, buffers, ledger и output directory. Кэш допускается только для immutable feature data с ключом dataset+algorithm+parameters; изменение профиля не читает чужой кэш.

Проверка parity: один набор параметров, один schedule, данные и fill model, одинаковый seed — совпадают решения ядра; одинаковые фактические fills при одинаковом исполнении — совпадают кампании/PnL. Если сами fill engines различаются, разница документируется, а не скрывается под ложным exact parity.

## Порядок разработки

Руководствоваться [AGENTS.md](../../AGENTS.md) и [coding guidelines](../../CONTEXT_CODING_GUIDELINES.md). Сохранять BOM/CRLF существующих файлов; новые MD — UTF-8/LF. Для публичных C# типов — XML documentation, не JavaDoc. Не внедрять новый DI framework или десятки пустых слоёв: названия компонентов обозначают ответственность, не обязательную иерархию классов.

Сборка основного проекта из `project`: `dotnet build OsEngine/OsEngine.csproj`. При затрагивании Tests и перед выпуском — `dotnet build OsEngine.sln`. Команды не выполнялись в документационной поставке. MCP test stand требует отдельного разрешения; его запуск может управлять экземплярами приложения и не является безвредной проверкой Markdown.
